# 如文写作系统 5.0 独立架构审计

## 结论

当前候选版**不建议按 5.0 正式版发布**。两入口、中文岗位、项目知识模型、作者资料包白名单和字符预算已经成形，正常路径测试也全部通过；但独立逆向检查复现了 4 类阻塞问题：原始输入隔离可绕过、未批准/越权资料可经状态协调进入章节情境来源、表现资源激活证据未绑定目标、正典与记忆门可以由脚本参数自行跨过。

审计对象为写报告时停止变更后的最终快照；排除 `__pycache__` 后共 60 个文件，树哈希为 `afa7c861e6a8dde3c43b43054c9fca721614390e1c1b2b21f2bd45a560a92646`。

验证结果：现有 16 项单元测试全部通过；两个 Skill 均通过 `quick_validate.py`。这说明正常路径可运行，不代表下述逆向路径已被覆盖。

## 阻塞问题

### B1. 原始输入与干净委托的隔离只检查字段名，原文换一个键即可通过

- `scripts/handoff_validator.py:40-51` 的 `nested_keys()` 只收集键名；`scripts/handoff_validator.py:78-85` 也只将键名与禁止词集合比较，不检查字符串值，也没有为六种交接物定义各自的 payload 白名单。
- 已复现：把完整原始用户消息放入 `payload.content`，同时保留 `creative_value`，并设置 `approval: "approved"`，`validate(..., for_execution=True)` 返回零错误。
- `scripts/handoff_validator.py:72-75` 还把交接物自身声明的字符串 `approved` 当成执行许可，没有外部审批记录或哈希绑定。
- 这直接违反 `shared/information-contract.md:25-27` 和 `shared/creative-communication-contract.md:11-23` 的防双重输入要求。

建议：为每种 kind 定义严格 payload schema；原始输入只存在于上游隔离上下文，不允许自由文本容器；执行审批引用独立、不可由交接物自声明的审批事件。

### B2. 项目就绪与状态协调可把占位、未批准及研究资料带入章节情境来源

- `scripts/project_readiness.py:48-56` 只检查世界总表章节长度和“世界/系统”下存在任意 Markdown；没有拒绝“待用户确认”，也不检查系统内容、注册、状态或审批。
- `scripts/project_readiness.py:57-62` 只强制项目声音 active；项目章程、主角档案、世界总表、当前态势、世界系统和故事弧均不要求 active/approved。
- 已复现：仅补足主角三段文字、伪造项目声音为 active，保留模板中的项目章程、世界总表、当前态势和核心系统占位文字，`project_readiness.check()` 仍返回 ready。
- `scripts/story_state.py:537-546` 初始化时只限制 tracked source 的目录前缀，不核对资源 ID、owner、active、approval 或作用域；active outline 也只要求位于 `故事/`。
- 更严重的是 `scripts/story_state.py:753-800` 的 `reconcile_state()` 没有重复初始化时的目录禁区和注册表检查。已复现将 `研究/README.md` 同时设为 active outline 与 tracked source，状态保存成功。

结果是研究、未批准故事或占位世界资料能够成为 generation field 的声明来源，随后作者包只看投影哈希，无法恢复来源是否合法。

建议：项目就绪按必需资源 ID 检查 active、approved、哈希、作用域与内容占位；初始化和 reconcile 共用同一注册资源选择器，outline 必须是 active story 资源，tracked source 必须是 active/approved 且职责合法。

### B3. 表现资源的闭合审计与非正典试写证据没有绑定目标资源

- `scripts/resource_registry.py:223-242` 激活 expression 时只检查任意 JSON 中 `pass=true`、`user_accepted=true`、`canonical=false`，没有核对闭合报告的 `path`、`sha256` 是否等于被激活资源，也没有核对试写使用了哪个资源版本。
- `scripts/resource_registry.py:148-155` 后续验证只核对证据文件自身哈希，不解析证据内容，也不绑定当前资源哈希。
- 已复现：两个最小手写 JSON（一个仅有 `pass:true`，另一个仅有试写三个布尔状态）即可通过 transition 并激活项目声音。
- `scripts/resource_registry.py:20-21, 200-225` 允许 `proposed -> candidate` 时完全不要求闭合审计，与 `skills/ruwen-gushi-gousi/references/external-knowledge-and-expression.md:23-32` 的“审计通过后才 candidate”冲突。
- `scripts/closure_audit.py:13-39` 本身只是少量正则预检，却被激活流程当成完整六项审计的充分证明。

建议：闭合报告必须包含并校验目标 resource ID、路径、版本、当前 source SHA-256、六项独立结论；试写报告绑定同一资源哈希和试写产物；candidate 转换即要求有效闭合报告；语义审计不能只由正则自动判定。

### B4. 正典提升目标与批准后记忆门可被脚本参数直接跨过

- `scripts/story_state.py:627-665` 的 `record_approved()` 没有用户批准参数或审批事件引用，调用函数即写入 `approved_at`。
- `scripts/story_state.py:679-750` 的 `promote_approved()` 允许把候选正文写到项目内任意、但不在 `authoring-ruwen-v5/` 下的 Markdown。它没有限定正式章节目录，因此可覆盖 `项目/项目章程.md`、`故事/当前故事弧.md`、`表现/项目声音.md` 等权威资料。
- `scripts/story_state.py:796-800` 仅凭 `clear_pending=True` 清除 `pending_consolidation`；`scripts/story_state.py:847-856` 暴露 `--clear-pending`，没有记忆变更预览、第二次用户批准或审计账本事件的证明。
- 现有测试 `scripts/test_ruwen_v5.py:145-158` 正是直接调用 `record_approved()`，再以 `reconcile_state(..., True)` 清门，因此测试固化了绕过路径。

建议：批准候选与清除记忆待处理状态都必须引用独立审批事件；正式正文目标限定在唯一规范目录；提升前验证候选、作者包和审批事件链；清门必须验证已批准的记忆变更提交及审计记录。

## 重要问题

### I1. 活跃表现资源的合法修改路径会自毁激活证据

- `scripts/resource_registry.py:256-274` 的 `refresh_hash()` 会把 approval 整体替换成仅含批准人和时间的新对象，删除闭合审计及试写路径/哈希。
- 已复现：对 active 项目声音执行 refresh 后函数返回成功，但紧接着 `validate_registry()` 报两项“缺少可核验的激活证据”。
- 同时注册表禁止同一路径多资源（`scripts/resource_registry.py:129-135`），作者编译器又要求项目声音恰为 `表现/项目声音.md`（`scripts/compile_author_packet.py:117-130`），使项目声音版本替换没有完整、可用的正式路线。

### I2. 作用域冲突与 supersedes 只登记，不治理

- `scripts/resource_registry.py:156-161` 只检查 supersedes 指向的 ID 存在，不检查循环、版本方向、被替代资源是否转为 superseded、作用域是否相交。
- `scripts/resource_registry.py:181-197` 遇到多个有效表现能力时按排序静默保留第一个，而不是把同一作用域的权威冲突作为错误。虽然最终仍只有一项进入选择结果，但可能装载错误能力。

### I3. 两个 Skill 对根目录脚本的引用是失效相对路径

- `skills/ruwen-gushi-gousi/SKILL.md:48` 写 `scripts/project_readiness.py`。
- `skills/ruwen-zhangjie-xiezuo/SKILL.md:31` 写 `scripts/compile_author_packet.py`。
- 脚本实际在技能目录的 `../../scripts/`。相比同一文件中正确的 `../../shared/...` 引用，这两处会把代理引向不存在的 `skills/<skill>/scripts/`。

### I4. 审计账本与文学问题账本的文件分离存在，但写入工具不锁定各自目标

- `scripts/audit_ledger.py:18-34` 和 `scripts/problem_ledger.py:66-79` 都接受任意 `--ledger` 路径；可以互相写入对方账本，甚至写入项目内其他文件。
- `scripts/problem_ledger.py:29-47` 只检查缺少字段，不拒绝额外技术字段；`scripts/audit_ledger.py:12-29` 对创意内容只屏蔽少数固定词。
- `scripts/governance_check.py:64-73` 只校验审计账本顶层键，并仅检查 manifest 是否出现“文学问题账本”字样，不能发现内容复制或账本写错目标。

### I5. Silent floor 有明确合同与作者指令，但正典脚本没有守门

- 文本规则完整：`shared/information-contract.md:29-31`、`skills/ruwen-zhangjie-xiezuo/CREATIVE-SOUL.md:7-17`、`skills/ruwen-zhangjie-xiezuo/references/roles/xiaoshuo-zuozhe.md:3-5`。
- 但 `scripts/story_state.py:627-750` 对候选正文不检查治理说明、来源、自检清单或防御性履约语言；任意 Markdown 均可记录批准并提升。用户审批很重要，但 silent floor 被定义为系统底线，不应只靠提示词和最终肉眼发现。

### I6. “唯一顶层目录”与真实生成/正典目录相互矛盾

- `skills/ruwen-gushi-gousi/references/project-knowledge-model.md:3-5` 宣称项目只使用八个顶层目录。
- 模板实际另有 `authoring-ruwen-v5/`；测试与正式提升路径又使用未在模板或知识模型中定义的 `chapters/`（`scripts/test_ruwen_v5.py:151-171`）。
- 应明确区分“权威知识顶层”“工程临时目录”“正式正文目录”，并为正式正文给出唯一位置。

## 轻微问题

### M1. 创意委托允许发送给文学编辑，与读取矩阵不一致

- `scripts/handoff_validator.py:30-36` 允许 `creative_brief -> wenxue-bianji`。
- `shared/information-contract.md:17-23` 将故事构思师作为创意委托读者，文学编辑只应读正文、读者反应和按需诊断。若确有“当前候选局部修订委托”需求，应定义独立 kind，而不是复用创意委托。

### M2. 岗位参考文件没有从 Skill 入口显式路由

- 两个 `references/roles/` 目录包含关键岗位边界，但 Skill 只概述岗位，未说明何时读取对应角色文件。当前主体文字已重复大部分规则，因此不是立即失效；但这些文件作为渐进披露资源不易被发现。

### M3. 发布包包含 `scripts/__pycache__/` 与 `.pyc`

- 不影响运行，但会污染候选包、树哈希和跨 Python 版本分发，应在发布包排除。

## 已确认符合

- **两个用户入口**：插件 manifest、模板 `AGENTS.md` 和两个 `agents/openai.yaml` 均清楚区分“故事构思”与“章节写作”；章节入口也会把新增创意退回构思入口。
- **中文岗位名**：用户可见指令和岗位文件均使用中文岗位名；拼音 slug 仅作为工程标识。现有测试也确认旧英文岗位名未残留于生产技能文档。
- **项目知识骨架**：模板包含项目章程、主角客观存在/内在组织/叙述接口三模型、世界总表、当前态势和核心世界系统；职责拆分清晰。
- **作者资料包隔离**：`scripts/compile_author_packet.py:113-175, 249-270` 对项目声音、POV、关系镜头和表现能力执行路径、资源类型、active、allow_author、哈希与作用域检查；研究、治理、校验、世界和故事全文不能直接冒充这些岗位来源。
- **作者最多一项表现能力及预算**：manifest 只有一个 `expression_resource` 字段；编译器执行总计 8,000、generation field 2,200、项目声音 1,200、POV/可选镜头与能力 900、逐字文本 600 字符上限（`scripts/compile_author_packet.py:245-247, 277-280, 318-346, 363-369`）。
- **退役资源不进作者包**：作者包仅接受 active；现有退役测试通过。
- **候选稿与正典分离的基本状态机**：候选目录、待提升状态、正式替换前哈希核对与旧稿归档已经实现；问题在于审批证据、正式目标和记忆清门仍可绕过。
- **两类账本物理分离**：模板分别提供 `治理/审计账本.jsonl` 与 `治理/文学问题账本.jsonl`，文学问题跨任务复发统计逻辑也通过测试；问题是写入端未锁定目标。

## 发布建议

先修复 B1-B4 并增加对应逆向测试，再处理 I1-I3。至少应新增以下失败用例：通用键携带原始输入、占位世界通过 readiness、reconcile 读取研究、未绑定闭合证据激活、refresh active expression 后注册表失效、正典提升覆盖权威资料、无第二次审批清除 pending consolidation。修复后再重跑完整测试与独立审计。
