## 高严重度

### H-1 正文提升目标未限制在正式章节目录，可覆盖治理与设定 Markdown

- 定位：`scripts/story_state.py:699-708, 711-729`
- 原因：目标只要求位于项目根内、扩展名为 `.md`、且不在 `authoring-ruwen-v5` 下；没有要求位于 `chapters/`（或其他正式正文目录）。
- 复现：准备有效 packet 和候选正文后，调用 `promote_approved(..., "项目/项目章程.md", replace_existing=True, expected_target_sha256=<章程哈希>)`。
- 实际结果：调用成功，`项目/项目章程.md` 被候选正文覆盖；状态把该路径登记为 `last_approved_prose`，旧章程虽进入 replacement archive，但项目治理文件已被替换。
- 影响：审批提升获得超出“正式章节”职责的写权限，可改写项目章程、人物档案、世界设定、项目声音、硬设定规则等任意 Markdown 文件。
- 修复建议：引入状态中固定的正式正文根目录；目标必须是该目录的直接/受控后代；明确拒绝 `项目/`、`人物/`、`世界/`、`故事/`、`表现/`、`治理/`、`校验/` 与 `authoring-ruwen-v5/`。新增覆盖每个受保护目录的负向测试。

### H-2 “只读迁移预览”的 `--output` 可覆盖源项目任意文件

- 定位：`scripts/migrate_v4_1_preview.py:38-53`
- 原因：工具先扫描源树，再无边界、无冲突检查地执行 `Path(args.output).write_text(...)`。
- 复现：源项目含 `author-voice/project-core.md`，以该同一路径同时作为 `--output`。
- 实际结果：退出码 0，原文 `ORIGINAL` 被迁移 JSON 覆盖。
- 影响：与脚本“只读分析、不移动、不改写项目”的契约直接冲突；可覆盖旧项目正文、设定、状态或注册表。
- 修复建议：输出必须省略或位于源项目之外；解析后先拒绝任何 `output.resolve()` 位于 `project-root.resolve()` 内的情况，并用排他创建避免覆盖既有文件。现有测试只调用 `classify()`，没有执行 CLI，不能证明只读性。

### H-3 manifest 的章节作用域未绑定已注册 projection，作用域可自报绕过

- 定位：`scripts/compile_author_packet.py:240-268`；`scripts/resource_registry.py:165-173`
- 原因：编译器用 manifest 自报的 `context_scope` 选择资源，只校验 projection 路径等于 active projection；未校验 `context_scope.chapter == state.active_projection.chapter`，也未绑定项目、卷、弧、场景类型、POV 的可信来源。
- 复现：注册 projection 的章节为 `001`；把 POV 资源限制为 `chapters=["999"]`，同时把 manifest 的 `context_scope.chapter` 改为 `999`。
- 实际结果：packet 编译成功，尽管实际 active projection 是第 `001` 章。
- 影响：任意 manifest 编辑者可通过伪报 chapter/arc/POV 等字段加载本不适用于当前章节的资源。
- 修复建议：把可信作用域写入 state/projection metadata 并纳入哈希；编译时逐字段比较 manifest 与可信作用域，manifest 只可引用而不可声明权限事实。

### H-4 `check_packet` 可把任意自签名文件判为有效资料包

- 定位：`scripts/compile_author_packet.py:399-415`；`scripts/story_state.py:382-413`
- 原因：检查器不要求被查文件位于 packets 目录、不要求等于 `state.active_packet`，也不校验 metadata schema、manifest 或必需角色；只要旁置 meta 自报 artifact 哈希并给出空 `sources` 即可。
- 复现：在项目根写 `rogue.md`，旁置 `rogue.md.meta.json`：`{"artifact": <rogue 的路径与哈希>, "sources": []}`；然后调用 `check_packet(root, "rogue.md")`。
- 实际结果：返回 `{"valid": true, "reasons": []}`，而状态中的 active packet 仍是 `authoring-ruwen-v5/packets/current.md`。
- 影响：下游若把 `check` 当作可信入口，可接受未编译、无 manifest、无授权来源的伪造资料包。
- 修复建议：强制 packets 目录、active packet 路径与哈希完全一致；严格校验 meta schema、manifest 哈希及必需来源角色集合，拒绝未知/缺失字段。

## 中严重度

### M-1 表现资源激活证据未绑定目标资源

- 定位：`scripts/resource_registry.py:223-242, 148-155`
- 原因：激活时只检查审计 JSON 的 `pass=true` 和试写 JSON 的两个布尔值；不检查审计中的资源路径/哈希是否等于待激活资源，也不检查试写属于该资源。后续验证只验证证据文件自身哈希。
- 复现：用明确指向“项目声音”的审计文件和声明其他 resource id 的试写文件，激活新的 `表现/能力/新能力.md`。
- 实际结果：新能力变为 active，`governance_check` 仍返回 valid。
- 影响：一份证据可跨资源复用，未实际试写/批准的表现能力可被提升。
- 修复建议：定义严格证据 schema，绑定 `resource_id`、资源规范路径、资源 SHA-256、审计器版本；transition 与常态治理都验证这些字段。

### M-2 `refresh_hash` 成功返回后会把 active 表现资源写成注册表无效状态

- 定位：`scripts/resource_registry.py:256-274`
- 原因：刷新哈希时无条件重建 approval，仅保留 `status/approved_at/approved_by`，删除 active expression 必需的 closure/trial 证据。
- 复现：修改已激活项目声音，调用 `refresh_hash(..., approved=True)`。
- 实际结果：函数成功返回且资源仍为 active；紧接着 `validate_registry` 报两项“缺少可核验的激活证据”。
- 影响：一个报告成功的受支持命令会原子性地把项目推进到不可用状态。
- 修复建议：active expression 禁止直接 refresh，必须退回 candidate 并重新审计/试写；或在刷新命令中要求并重新绑定完整证据。写注册表应采用原子替换。

### M-3 `reconcile` 丢失初始化阶段的职责边界检查

- 定位：`scripts/story_state.py:765-784`，对照 `:537-546`
- 原因：初始化要求 outline 位于 `故事/`，并拒绝 tracked source 来自 `研究/治理/校验/authoring-ruwen-v5`；reconcile 更新相同字段时没有这些检查。
- 复现：初始化正常项目后，reconcile 使用 `outline=治理/审计账本.jsonl` 与 `leak=治理/文学问题账本.jsonl`。
- 实际结果：成功写入 state，二者分别成为 active outline 和 tracked source。
- 影响：重协调路径可把治理/私有账本重新标记为故事输入，破坏职责隔离并污染后续生成元数据。
- 修复建议：抽取一套共享的 outline/source 校验函数，init 与 reconcile 必须调用同一实现。

### M-4 技术审计账本允许嵌套原始输入，常态治理无法发现

- 定位：`scripts/audit_ledger.py:12-34`；`scripts/governance_check.py:64-69`
- 原因：追加器只限制顶层字段名并用少量中文词做全文黑名单；`scope` 等白名单字段可放任意嵌套对象。治理检查也只检查顶层字段名。
- 复现：事件的 `scope` 写入 `{"raw_user_input":"整段私人创作内容可藏在这里"}`。
- 实际结果：追加退出码 0；内容落盘；`governance_check` 返回 valid。
- 影响：本应只保存技术事件的治理账本可被创意内容、原始请求或隐私数据污染。
- 修复建议：对每个字段定义类型、枚举与长度；scope 使用固定键和标量；禁止任意嵌套对象。治理检查复用同一 schema，而非另写较弱规则。

### M-5 项目 ID 未转义即替换进 manifest，初始化可成功地产生坏项目

- 定位：`scripts/init_project.py:17-32`
- 原因：注册表通过 JSON 序列化写入 project id，但 manifest 使用纯字符串 `.replace()`。
- 复现：`--project-id 'bad"id'`。
- 实际结果：初始化退出码 0，但 `author-manifest.json` 无法解析（`Expecting ',' delimiter`）。
- 影响：合法命令行字符串可使刚初始化的模板不可用，且工具错误报告为成功。
- 修复建议：解析 manifest 模板为 JSON 后赋值并序列化；同时校验非空、长度和允许字符。初始化应在临时目录完成全部校验后再一次性发布。

## 其他已确认的测试缺口

以下问题也可复现，但优先级低于上述阻塞项：

- `story_state.py:627-664` 的 `record-approved` CLI 没有 `--approved-by-user` 或独立审批凭证；只要已有 active packet，调用者即可把任意 candidates 文件锁成“已批准”。实测命令退出 0 并设置 pending candidate。若调用层不能提供强审批保证，这属于审批自证。
- `handoff_validator.py:40-85` 只按嵌套键名拦截污染。把完整原始请求放在 `payload.brief` 可在 `for_execution=True` 时零错误通过；approval 同样只是文件中的自报字符串。
- `story_state.py:724-749` 先归档并替换正式目标，最后才保存 state；若最后一步因权限、磁盘或进程中断失败，会出现文件已替换而 state 仍 pending 的非事务状态。现有替换测试只覆盖成功路径和哈希不匹配，没有故障注入。
- `audit_ledger.py`、`problem_ledger.py` 的 `--ledger` 不是 project-root 相对路径且没有目录约束；调用者可向任意可写文件追加 JSON。建议改为 `--project-root` 加固定账本相对路径。

## 已确认有效的防护

- `story_state.resolve_under` 与 `resource_registry.normalize_path` 使用解析后的规范路径和 `relative_to`，常规绝对路径、`..` 与目录符号链接逃逸会被拒绝。
- 注册表会检查重复 ID、规范化后的重复路径、active/approved 基本关系、作者可读路径前缀和来源哈希。
- 正常替换路径要求目标哈希并保留归档；本次发现的问题是目标授权范围与失败原子性，不是成功路径缺少归档。
- 模板在普通 project id 下可实际复制，生成后的注册表哈希有效；readiness 在用户批准前正确保持 blocked。

至少修复 H-1 至 H-4 与 M-1/M-2，并增加 CLI 级回归测试后再重新评估。新增测试应真实执行命令而不只调用分类函数，覆盖：受保护目录目标、迁移输出回写、作用域伪报、伪造 packet meta、跨资源证据复用、active expression 刷新、reconcile 越权路径、账本嵌套污染和带引号 project id。
